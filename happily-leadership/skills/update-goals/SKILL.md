---
name: update-goals
description: Create and update your team's goals and key results in Happily, with every change previewed first. Covers recording a key result's latest value and note, setting its status, editing titles, targets, units, cycles and owners, adding or removing key results, archiving, replacing and restoring key results, creating goals (with up to 5 key results), linking goals to parent goals, archiving, restoring and permanently deleting goals, and undoing a change. Every change is previewed as an exact before → after and written only after the user confirms that preview. Also covers recording a newer number the user mentions in passing, and suggesting where a new goal or key result would help. Use whenever the user asks to create, update, change, correct, add, remove, delete or undo an OKR, goal or key result, mentions a new result for something a key result tracks, or asks whether any work should become a goal or key result.
---

Read [the evidence and cross-app guidance](../../references/evidence-and-context.md) and [the goal writing guide](../../references/goal-writing-guide.md). Changing a goal or key result is a write to Happily. An incorrect write is unacceptable, so follow this flow every time, even when the user says "just do it" or "no need to confirm".

1. **Preview first.** Call `propose_goal_change` with the team, the goal or key result as the user named it, and one `change`, or `propose_goal_changes` for several changes at once (step 5). It writes nothing. If several key results or goals match, the result is `needs_clarification`. Show the candidates and ask which one is meant. Never pick one yourself, even if one looks likelier. Re-propose with the chosen `kr_ref` or `goal_ref`.
2. **Pass only what the user said.** Never infer or round a value, target, unit, owner or cycle. A note may be drafted, but only from what the user said in this conversation (see **Update notes** below); never invent a reason, cause or next step. If a required number or field is missing (`missing_fields`), ask for it. If the unit differs from the key result's (`unit_mismatch`), ask the user to restate it. Don't convert it yourself.
3. **Show the preview.** Show the server's `preview_markdown` exactly as returned. It already has the heading, the location, the before → after table, the note, what else happens, and suggestions. Don't rebuild the table or paraphrase the numbers. Then ask one plain question, e.g. "Apply this change?". If `suggestions` are present, you may add one short line offering to improve the wording, but the question is about this preview as it stands.
4. **Apply only on a yes to that preview.** Call `apply_goal_change` with that preview's `confirmation_token` only after the user explicitly confirms *this* preview in their latest message. A yes to an earlier or different preview doesn't count, and neither does a general instruction given before the preview existed. If the user corrects anything, propose again and show the new preview.
5. **Several changes: one preview, one yes.** When the user asks for several updates on one team's goals together (each owner's number on a shared key result, progress on several key results, a round of status changes), use `propose_goal_changes` with all of them, up to 10. It returns one preview listing every change in order, and `apply_goal_change` with its token writes them all together, or none. Show the whole `preview_markdown` and ask once ("Apply these changes?"). If the user wants to drop or change one item, propose the batch again without it. Creating, deleting, re-linking and undoing stay one at a time with `propose_goal_change`; so do changes on different teams. Don't split a batch into separate previews unless the user asks.
6. **Report honestly.** After `applied`, show `result_markdown` (or say in one line what was written), and mention that it can be undone. Never say something was updated unless `apply_goal_change` returned `applied` or `already_applied`.

Update notes:

- **Offer one.** A progress update without a note is a bare number. When the user gives a value and has said why it moved or what's next, offer a short note built from their own words and put it in the change; it appears in the preview, where they can confirm, edit or drop it. If they've said nothing about why, ask in one line ("Want to add a note on what moved it?"); a value with no note is fine.
- **Write for where it lands.** The whole team reads the note on the key result's timeline, in the console and the mobile app. The owner's manager and any co-owners get a push notification that quotes only the first 140 characters, so lead with the key fact. Keep it to one to three sentences (about 280 characters; 500 at most), work facts only: nothing personal, private or about another person's performance.
- **Who is told.** The preview's `side_effects` say who gets notified. With a note or a status change, the owner's manager is told right away; a bare value change waits for their weekly digest. Undoing an update adds an "Undid an earlier update" entry, which notifies the same way.

Updating between scheduled rounds:

A key result doesn't have to wait for its weekly or monthly refresh. Offer an update when there's a reason now:

- **The user states a newer number**, in passing or while recognizing someone ("pages are down to 12 a week"). Preview it straight away with `propose_goal_change` (a preview writes nothing), show the server's preview and ask once whether to apply it. Don't describe the change in your own table first.
- **Work linked to the goal was finished after the key result was last updated** (`kr_update_opportunities` from `get_leader_digest`, or a done goal-linked focus item from `get_person_goal_progress`). That is a reason to ask the owner or user for the current number, not a number itself.
- **The key result has an update recipe** and its source is connected. Use [keep-key-results-current](../keep-key-results-current/SKILL.md) for that one key result now.

Responsibly means: the number comes from the user or the source, never inferred from finished work, a recognition message or a note; the note says where the number came from ("Priya, 30 Oct: 12 pages this week"); it is previewed and applied only on a yes, as above; and you mention that the owner's manager will be told when the preview's `side_effects` say so. Only offer once per key result per conversation. Scheduled runs only offer: the preview is made when the user says yes.

Suggesting a goal or key result:

Start with `get_leader_digest`: its `goal_suggestions` already lists work outside goals, people without a key result, teams without goals and cycles ending with nothing next, in one read instead of one per person. `get_person_goal_progress` gives the same for one person (`highlights.work_outside_goals`). Also look for goal-linked work that none of the goal's key results measures. Use these to give a heads-up, never to create anything on your own:

- **Work outside goals** (`work_outside_goals`): first ask whether the work belongs under an existing goal. If it does, the person can link the focus item ([update-focus](../update-focus/SKILL.md) for a manager's suggestion). If it's a real outcome nobody tracks, draft one key result as text using the writing guide, with a baseline, target, unit, owner and cycle for the user to fill or confirm.
- **Someone owns no key result** (`no_key_result`): suggest which existing key result they could co-own, or a draft one based on their focus work.
- **A team has no goals of its own** (`team_without_goals`): mention it once; inherited goals may be fine.
- **A cycle is ending with nothing next** (`next_cycle_due`): offer to draft next cycle's key results from this cycle's results.

Give suggestions as text first. Propose `create_goal` or `add_key_result` only with what the user chooses and confirms, as described below.

Creating and removing goals:

- **Writing well.** When the user is drafting a goal, key result or note, use the writing guide: goal titles state an outcome in 30 characters or fewer, key result titles carry their target, notes say what moved, why and what's next. Offer improvements as suggestions; the user's words go into the change unless they agree to a new version.
- **Create.** Use `create_goal` with the title and description the user gave, and only the key results they spelled out. Each key result needs a title, starting value, target, unit, owners and cycle (a standard needs no starting value; see below). Ask for any that are missing; never draft key results into the change yourself. If the user wants suggestions, give them as text first and propose only what they choose. Titles are capped at 30 characters (`invalid_title`): suggest a shorter one and keep the detail in the description.
- **Baseline versus current result.** `start_value` is the baseline the period is measured from; `current_value` is the result reached so far. "7 of 40 leads this quarter" is start 0, current 7, target 40, which is 17.5%. Never put a result already reached into the starting value to make it show: progress is measured from the start, so that shows 0%. A count within the period usually has a zero baseline, but confirm it with the user, and never assume zero for costs or other numbers that go down. When the user states a result already reached, pass it as `current_value` (or `owner_values` per owner on an individual key result), with a note on where it came from and when. It is recorded as the key result's first update.
- **Standards and key results not measured yet.** Some key results hold a level instead of reaching one: "keep uptime at least 99%" is `target_type: "maintain_at_least"` with the standard as `target_value`; "keep p95 at or under 3000ms" is `stay_at_or_below`. Use a standard only when the user describes holding a level. A standard is one shared value. Its starting value is an optional baseline: leave it out unless the user gave one. It needs the latest measurement as `current_value`. When the user says a number hasn't been measured yet, set `awaiting_measurement: true` and no `current_value`. It is created as "Not measured yet", shows as Awaiting first measurement, and stays out of progress until the first `update_progress`. That works for progress key results too (they still need a starting value), but only with one shared value. Never enter 0 or any other number for a value nobody knows. "Maintain at least" and "Not measured yet" need the company's service standards turned on; on `feature_not_enabled`, tell the user and don't work around it.
- **One key result, a target per person.** When several people each own part of a number (for example a team pipeline split across sellers), use one key result with `mode: "individual"` and give each person's target in `owner_targets`, by email. Owners left out get an even share of the team target. Pass only targets the user stated; if they don't add up to the team target, the preview warns, so point that out. To change targets later, use `edit_key_result` with `owner_targets`.
- **Numbers that live in another app.** When a key result's number comes from HubSpot, a spreadsheet or another connected tool, offer to record how it's updated so it can be refreshed in one step later. That's the [keep-key-results-current skill](../keep-key-results-current/SKILL.md).
- **Parent goals** must be goals on a team above this one. Pass them as the user named them; on `needs_clarification`, ask which one is meant.
- **Retire a key result.** When a key result no longer applies but its history should stay, archive it instead of removing it: `archive_key_result` with the `reason` the user gave (`priority_changed`, `no_longer_relevant` or `other`) and an optional `note`. When another key result on the same team takes over from it, use `supersede_key_result` with that key result as `replacement` (title or `kr_ref`); a superseded key result no longer counts toward Performance, its work lives on in the replacement. Both keep the values and update history, never mark it completed, and pause any automation. `restore_key_result` brings it back; automation stays paused until someone switches it on in Happily. Use `remove_key_result` only when the user asks to delete the key result and its history.
- **Delete.** "Delete" or "remove" a goal means archiving it first (`archive_goal`), which hides it and can be restored. Only archived goals can be deleted permanently (`goal_not_archived` otherwise). Propose `delete_goal` only when the user explicitly asks for permanent deletion of an archived goal, and show the `side_effects` about focus items and goals that still link to it.

Handling results:

- `conflict`: someone changed it after the preview, and nothing was written. Tell the user what changed (`what_changed`), and offer a fresh preview with current values.
- `expired` or `invalid_token`: propose again and ask the user to confirm the new preview.
- `scope_denied`: say who can make this change (from `reason`). Don't retry another way.
- `write_not_granted` or `not_configured`: this connection can't change goals. Give the user the exact update to enter in Happily themselves.
- `kr_archived`: that key result is archived. Offer to restore it first (`restore_key_result`).
- `replacement_required`, `replacement_missing`, `replacement_self`, `replacement_archived`: ask which active key result on the same team replaces it. `already_archived`: restore it before archiving it differently.
- `feature_not_enabled`: service standards aren't turned on for this company, so "Maintain at least" and "Not measured yet" key results can't be created here. Say so. Don't swap in a progress key result or a made-up number unless the user asks for that.
- `automated_kr`, `kr_in_history`, `goal_archived`, `goal_not_archived`, `invalid_parent`, `legacy_goal_ids`: explain the reason. Don't work around it.
- `cannot_revert` on undoing a create: the goal was changed since, so offer to archive it instead.
- In a batch, any refusal or `conflict` names the `item` it is about, and nothing in the batch was written. Explain that item, then offer a fresh batch preview.
- `not_batchable`: that kind can't be in a batch; preview it on its own.
- `not_confirmed`: the user declined in their app's confirmation prompt. Nothing was written.
- Undo: `propose_goal_change` with `change.kind` `revert_change` and the earlier `change_id` previews the undo, which is confirmed like any other change.

To read goals before or after a change, use `get_team_goals` or `get_kr_progress_history`. A `needs_clarification` result often lists the same key result for several cycles; show each candidate's cycle so the user can pick, and point out that past cycles are read-only. Set `include_archived: true` to see archived goals and archived key results (with their reason and what replaced them), for example after archiving or undoing a delete. Don't use these tools to "check" by applying.
